# Architecture

C4 levels 1 and 2. Mermaid has no C4 model, so the discipline is convention (ADR-0016):
one diagram per level, a fixed legend, no diagram over twelve nodes.

## Level 1 — context

```mermaid
flowchart LR
  owner([Business owner])
  staff([Agency staff])
  PG[PermitPortal]
  law[(Federal regulatory text<br/>eCFR / GPO bulk XML)]
  state[(State code and<br/>licence catalogues)]
  muni[(Municipal code)]
  census[(Classification schemes<br/>and crosswalks)]
  cred[(Credential vocabulary<br/>registry)]

  owner -->|describes the business<br/>confirms classification| PG
  staff -->|curates rules<br/>reviews escalations| PG
  PG -->|ordered obligations<br/>and credential chain| owner
  law --> PG
  state --> PG
  muni --> PG
  census --> PG
  cred --> PG
```

PermitPortal reads authoritative public sources and writes nothing back to them. It files
nothing on anyone's behalf (`01-vision-and-problem.md`, non-goals).

## Level 2 — containers

```mermaid
flowchart TB
  subgraph edge[Presentation]
    web[Reference UI<br/><i>Next.js</i>]
  end
  subgraph intel[Assistance plane — models allowed]
    cls[Classifier service<br/><i>Python</i>]
    exp[Explainer<br/><i>constrained to the evidence tree</i>]
  end
  subgraph det[Decision plane — no model dependency]
    res[Resolver service<br/><i>Go, CEL partial activation</i>]
    rules[(Rule data<br/>lists, credentials)]
  end
  subgraph store[Storage]
    pg[(Postgres<br/><i>bitemporal, CHECK-constrained</i>)]
  end
  subgraph ingest[Ingestion]
    ing[Source ingestion<br/><i>bulk XML, deltas</i>]
  end

  web --> cls
  web --> res
  cls -->|ranked candidates| web
  web -->|confirmed code of record| res
  res --> rules
  res --> pg
  cls --> pg
  res -->|evidence tree| exp
  exp --> web
  ing --> pg
```

The vertical split is the architecture. Everything in the **assistance plane** may call
a model. Nothing in the **decision plane** may — `packages/rules/engine` declares zero
model-client dependencies, and `scripts/check-engine-purity.py` fails the build on any
model-client import or manifest dependency there (ADR-0001).

Note the direction of the arrows between the planes. The classifier hands candidates to
the UI, not to the resolver. The resolver receives only a **confirmed** code of record.
The explainer receives an already-computed evidence tree and may only render nodes
present in it. There is no path by which a model output reaches a determination.

## Determination sequence

```mermaid
sequenceDiagram
  actor Owner
  participant UI
  participant Classifier
  participant Resolver
  participant DB as Postgres

  Owner->>UI: free-text description
  UI->>Classifier: describe
  Classifier->>Classifier: retrieve top-50, rerank to top-k
  Classifier-->>UI: ranked candidates + confidence
  UI-->>Owner: candidates in plain language, plus "none of these"
  Owner->>UI: confirms one
  UI->>DB: assignment (owner_confirmed, is_code_of_record)
  UI->>Resolver: resolve(subject, as_of_law)
  Resolver->>DB: facts + ruleset version
  Resolver->>Resolver: evaluate with partial activation
  alt facts missing
    Resolver-->>UI: INDETERMINATE + missing_attributes[]
    UI-->>Owner: the next question
  else evaluable
    Resolver->>DB: determination + evidence tree + input hash
    Resolver-->>UI: obligations + ordered credential DAG
    UI-->>Owner: what to obtain, in what order, with citations
  end
```

The loop back through "the next question" is the product. A system that cannot say *what
it still needs to know* has to guess, and guessing here is how a business gets fined.

## What is deliberately absent

- **No level 4.** There is no application code yet, and a component diagram of code that
  does not exist is a claim this repository's status discipline forbids.
- **No graph database.** ADR-0011.
- **No message bus.** Determination is synchronous and sub-second by design; ingestion is
  a scheduled batch. Adding a bus before there is a queueing problem buys an operational
  surface in exchange for nothing measurable.
